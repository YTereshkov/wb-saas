# AGENTS.md — SellerScope

## О проекте

Этот репозиторий содержит **SellerScope** — SaaS-сервис аналитики для продавцов Wildberries.

Это полностью отдельный проект, не связанный со SmartBett.

Никогда не переноси сюда и не применяй автоматически:

- архитектуру SmartBett;
- ограничения Symfony 3.4;
- ограничения старых версий PHP из SmartBett;
- инфраструктуру SmartBett;
- доменную логику SmartBett;
- код SmartBett;
- соглашения и структуру SmartBett.

# Утверждённая архитектура

SellerScope — это **модульный монолит**.

Проект должен оставаться:

- одним Git-репозиторием;
- одним Laravel-приложением;
- одной кодовой базой для deployment;
- backend и frontend находятся внутри одного проекта.

Утверждённый стек:

- Laravel 13;
- PHP;
- Inertia.js 3;
- React 19;
- TypeScript;
- Tailwind CSS 4;
- shadcn/ui;
- Recharts;
- PostgreSQL;
- Redis;
- Laravel Queue;
- Laravel Horizon;
- Laravel Scheduler;
- Docker Compose.

Без явного согласования не добавляй:

- Next.js;
- отдельный frontend;
- отдельный backend;
- микросервисы;
- отдельный SPA с собственным REST API между нашим Laravel и React, если Inertia решает задачу;
- GraphQL;
- CQRS;
- Event Sourcing;
- Kubernetes;
- чрезмерное DDD;
- инфраструктуру для гипотетической нагрузки, которой пока нет.

Предпочитай максимально простую архитектуру, которая чисто решает текущие задачи продукта.

Laravel отвечает за:

- authentication;
- authorization;
- validation;
- бизнес-логику;
- интеграцию с Wildberries;
- работу с базой данных;

- синхронизацию;

- операции, связанные с безопасностью.

React отвечает за:

- отображение интерфейса;
- пользовательские взаимодействия;
- локальное состояние UI;
- графики;
- таблицы;
- фильтры;
- визуальное поведение компонентов.

Inertia.js является стандартным способом связи Laravel и React внутри SellerScope.

Не создавай ненужные API-endpoints только для связи нашего собственного Laravel backend с нашим собственным React frontend.

Не размещай бизнес-логику внутри React-компонентов.

Не рассчитывай авторитетные бизнес-метрики в браузере.

По возможности передавай во frontend уже подготовленные и агрегированные данные.

# Интеграция с Wildberries

Frontend никогда не должен напрямую зависеть от формата ответов Wildberries API.

Интеграция с Wildberries должна быть изолирована отдельным слоем приложения.

Предпочтительная абстракция:

`WildberriesClientInterface`

с реализациями по смыслу:

- `DemoWildberriesClient`
- `WildberriesClient`

Конкретные названия классов могут измениться, если утверждённая архитектура проекта предусматривает более подходящую структуру.

Остальная часть приложения должна работать с нашими нормализованными данными, а не напрямую с сырыми ответами Wildberries API.

React никогда не должен обращаться к Wildberries API напрямую.

# Demo-режим

Первая версия продукта может работать на demo-данных.

Но demo-режим должен использовать нормальную архитектуру приложения.

Запрещено:

- хранить большие fake-массивы непосредственно внутри React-компонентов;
- генерировать случайные несвязанные значения при каждом запросе;
- делать отдельную frontend-only бизнес-логику для demo;
- привязывать UI к структурам, существующим только для demo.

Demo-данные должны быть:

- стабильными;
- воспроизводимыми;
- логически связанными между собой;
- реалистичными.

Предпочитай Laravel seeders, factories и backend demo providers.

Переход от demo-данных к реальным данным Wildberries не должен требовать переписывания UI.

# Данные и аналитика

Не передавай в React огромные массивы сырых данных, если экрану нужны только агрегированные показатели.

Предпочтительная схема:

`Wildberries`
→ `import`
→ `normalization`
→ `database`
→ `aggregation`
→ `application service`
→ `Inertia props`
→ `React UI`

По возможности концептуально разделяй:

- исходные импортированные данные;
- нормализованные данные SellerScope;
- производные аналитические показатели.

Не создавай сложное аналитическое хранилище заранее.

PostgreSQL является основной базой данных до тех пор, пока реальные измерения не покажут необходимость в другой технологии.

Избегай:

- N+1 запросов;
- неограниченных выборок;
- загрузки десятков тысяч строк в браузер без необходимости.

Для крупных таблиц pagination, filtering и sorting по умолчанию должны выполняться на backend.

Операции, связанные с:

- внешними API;
- синхронизацией;
- повторными попытками;
- обработкой отчётов;

Интеграция с Wildberries должна учитывать:

- rate limits;
- retries;
- timeouts;
- обработку ошибок;
- idempotency;
- состояние синхронизации;
- логирование.

Не создавай агрессивные retry-loop и бесконтрольный polling.

# Безопасность

SellerScope — многопользовательский SaaS.

Изоляция данных между продавцами является критически важным требованием.

Один пользователь никогда не должен получить доступ к данным другого продавца через:

- подмену ID;
- изменение request parameters;
- Inertia props;
- controller endpoints;
- background jobs;
- exports;
- прямые запросы к URL.

Authorization всегда должна проверяться на backend.

Нельзя полагаться на frontend для контроля доступа.

Токены и credentials Wildberries считаются чувствительными данными.

Запрещено:

- без необходимости передавать их в React;
- писать их в логи;
- коммитить их;
- помещать реальные credentials в seeders или fixtures;
- хранить их открытым текстом, если возможно безопасное шифрованное хранение.

Secrets должны храниться через environment/configuration-механизмы, а не в исходном коде.

# Правила frontend-разработки

Следуй утверждённой Design System.

Создавай reusable components там, где реально существует повторное использование.

Не создавай abstraction только потому, что два элемента немного похожи.

Страницы должны состоять из разумных компонентов.

Избегай огромных React-компонентов, содержащих весь экран целиком.

Предпочтительная структура:

- Pages;
- Layouts;
- feature-компоненты;
- shared UI primitives;
- chart components;
- table components;
- hooks/helpers, когда они действительно нужны.

Используй TypeScript полноценно.

Не применяй `any` только ради того, чтобы убрать ошибки TypeScript.

`any` допустим только на действительно сложной внешней границе и должен быть обоснован.

shadcn/ui — это набор базовых компонентов, а не готовый дизайн SellerScope.

Компоненты shadcn/ui необходимо адаптировать под утверждённую Design System.

Не позволяй стандартному виду shadcn/ui заменить утверждённые mockups.
