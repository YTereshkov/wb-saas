# SellerScope — метрики и формулы MVP

Статус: утверждённая основа аналитики Demo-MVP  
Последнее обновление: 14 августа 2026 года

## 1. Назначение

Документ задаёт единую семантику показателей SellerScope. Backend, Inertia
ViewModel, tooltip, таблицы и тесты должны использовать эти определения.
Frontend не пересчитывает authoritative metrics.

Связанные источники:

- [архитектура приложения](../architecture.md);
- [UX/UI Specification](../design/ux-ui-spec.md);
- [Design System](../design/design-system.md).

Если внешний отчёт Wildberries использует похожее название с другой
семантикой, UI SellerScope всё равно следует определениям ниже. Отличия должны
устраняться в normalizer, а не в React.

## 2. Канонические термины

| Термин       | Значение в SellerScope                                                        |
| ------------ | ----------------------------------------------------------------------------- |
| Заказы       | Оформленные покупателями единицы (`Order`)                                    |
| Продажи      | Состоявшиеся продажи или выкупленные единицы (`Sale`)                         |
| Выручка      | Сумма состоявшихся продаж; не прибыль и не сумма после вычета возвратов       |
| Выкуп        | Доля продаж от заказов за выбранные event-date диапазоны                      |
| Возвраты     | Возвраты после состоявшейся продажи (`ReturnFact`), а не невыкупленные заказы |
| Не выкуплено | Неотрицательная разница между заказанными и проданными единицами              |
| Остаток      | Физическое количество товара по последнему доступному снимку                  |
| Запас, дней  | Прогноз покрытия текущего остатка при среднем темпе продаж                    |

Заказы, продажи и возвраты остаются разными фактами. Они не объединяются в одну
таблицу событий и не подменяют друг друга при изменении позднего статуса.

## 3. Общие правила расчёта

### 3.1 Период и timezone

- timestamps сохраняются в UTC;
- попадание факта в business date определяется timezone `SellerAccount`;
- диапазон дат включителен с обеих сторон;
- количество дней периода — число календарных business dates, включая дни без
  событий;
- дневная агрегация использует business date кабинета;
- недельная агрегация объединяет готовые daily metrics, неделя начинается в
  понедельник;
- неполная неделя на краю диапазона не дополняется днями вне выбранного периода.

`AnalyticsPeriod` всегда содержит текущий диапазон, comparison range, timezone
и granularity. Запрос не должен смешивать данные разных экземпляров
`AnalyticsPeriod`.

### 3.2 Event date

| Факт          | Поле включения в период                                           |
| ------------- | ----------------------------------------------------------------- |
| Order         | `ordered_at`                                                      |
| Sale          | `sold_at`                                                         |
| ReturnFact    | `returned_at`                                                     |
| StockSnapshot | `snapshot_at`, с отдельным effective `as_of` для текущего остатка |

Выкуп MVP — операционное отношение событий выбранного периода, а не cohort
analysis одних и тех же заказов. Между оформлением заказа и продажей существует
временной лаг, поэтому UI обязан показывать соответствующую оговорку.

### 3.3 Числовые типы

- деньги хранятся и суммируются в целых копейках;
- деление выполняется decimal arithmetic с достаточной внутренней точностью;
- binary floating point не сохраняется как authoritative value;
- округление применяется только после полного расчёта, а не к каждому факту;
- quantity факта должно быть неотрицательным целым числом после normalization.

## 4. Основные KPI

В формулах:

- `P` — текущий выбранный период;
- `O(P)` — нормализованные Order facts периода;
- `S(P)` — нормализованные Sale facts периода;
- `R(P)` — нормализованные ReturnFact периода;
- `quantity(f)` — число единиц факта;
- `amount(f)` — сумма факта в копейках.

### 4.1 Выручка

```text
Revenue(P) = Σ amount(s), где s ∈ S(P)
```

Правила:

- используется `sold_at`;
- возвраты не вычитаются;
- комиссия, логистика, себестоимость и налоги не вычитаются;
- отрицательный или отменённый source record должен быть классифицирован
  normalizer, а не неявно менять формулу;
- UI называет показатель «Выручка», а не «Прибыль» или «Чистая выручка».

### 4.2 Заказы

```text
Orders(P) = Σ quantity(o), где o ∈ O(P)
```

Показатель отражает оформленные единицы. Последующая продажа, отмена или
невыкуп не удаляет факт оформления из исторического периода; его состояние
может использоваться в дополнительном объяснении.

### 4.3 Продажи

```text
Sales(P) = Σ quantity(s), где s ∈ S(P)
```

Используется дата состоявшейся продажи `sold_at`, а не дата исходного заказа.

### 4.4 Выкуп

```text
Buyout(P) = Sales(P) / Orders(P) × 100%
```

Если `Orders(P) = 0`, показатель равен `null`, а не `0%`. ViewModel передаёт
признак недоступного denominator; UI показывает нейтральное отсутствие значения
и не выводит бесконечность.

### 4.5 Возвраты

```text
Returns(P) = Σ quantity(r), где r ∈ R(P)
```

Возврат учитывается по `returned_at`. Он не уменьшает `Sales(P)` и
`Revenue(P)`.

### 4.6 Доля возвратов

```text
ReturnsRate(P) = Returns(P) / Sales(P) × 100%
```

Если `Sales(P) = 0`, значение равно `null`.

### 4.7 Не выкуплено

```text
NotBought(P) = max(Orders(P) - Sales(P), 0)
```

Нижняя граница защищает UI от отрицательного значения при временном лаге,
backfill или несовпадающих event-date диапазонах. Метрика не является отдельным
ReturnFact.

## 5. Сравнение периодов

### 5.1 Выбор comparison range

- для полного календарного месяца используется предыдущий календарный месяц;
- для произвольного диапазона используется непосредственно предшествующий
  диапазон той же длины;
- границы рассчитываются в timezone кабинета.

Пример: `1–31 июля 2026` сравнивается с `1–30 июня 2026`, а произвольный период
`10–16 июля` — с `3–9 июля`.

### 5.2 Относительное изменение

Для денег и количеств:

```text
RelativeChange(current, previous)
    = (current - previous) / previous × 100%
```

Если `previous = 0`, относительное изменение равно `null`. UI не показывает
`∞%`; ViewModel отдельно сообщает, что comparison percentage недоступен.

### 5.3 Изменение доли

Для Buyout и Returns Rate используется разница в процентных пунктах:

```text
PercentagePointChange(currentRate, previousRate)
    = currentRate - previousRate
```

Если хотя бы одна доля равна `null`, изменение также равно `null`.

### 5.4 Атомарность

KPI, comparison, chart series, product contributions и главный сигнал одной
страницы рассчитываются для одного `AnalyticsPeriod` и одной data revision.
Старые KPI нельзя показывать вместе с графиком нового периода.

## 6. Продажи по дням и неделям

`AccountDailyMetric` и `ProductDailyMetric` хранят дневные значения Revenue,
Orders, Sales и Returns.

Day grouping читает daily metrics напрямую. Week grouping суммирует те же
дневные строки внутри недельных buckets. Переключение day/week не меняет
семантику показателя и не выполняет повторную интерпретацию сырых WB payload.

Дни без фактов присутствуют в временном ряду с нулевым значением, если ресурс
успешно синхронизирован. При missing/partial resource ноль не подменяет
неизвестное значение: секция получает data-quality state.

## 7. Остатки и прогноз

В формулах:

- `CurrentStock(product, asOf)` — сумма quantity по складам из последнего
  согласованного снимка товара;
- `ProductSales(P)` — продажи товара за период;
- `Days(P)` — число календарных дней периода;
- горизонт рекомендации MVP — фиксированные 30 дней.

### 7.1 Средние продажи в день

```text
AverageDailySales(product, P)
    = ProductSales(product, P) / Days(P)
```

В denominator входят все календарные дни, включая дни без продаж. Неполный или
недоступный sales resource не преобразуется в ноль без data-quality marker.

### 7.2 Запас в днях

```text
StockCoverage(product, P, asOf)
    = CurrentStock(product, asOf) / AverageDailySales(product, P)
```

Поведение крайних случаев:

- если текущий остаток равен нулю, а средние продажи положительны, coverage
  равен `0`;
- если средние продажи равны нулю, coverage равен `null` с причиной
  `no_sales`, а не бесконечности;
- если stock snapshot отсутствует или устарел, значение не считается
  authoritative и сопровождается missing/stale state.

Для classification используется точное decimal value до UI-округления.

### 7.3 Рекомендуемая поставка

```text
RecommendedSupply(product, P)
    = max(0, AverageDailySales(product, P) × 30
             - CurrentStock(product, asOf))
```

Для отображения количества результат округляется вверх до целой единицы только
после расчёта. Если средние продажи равны нулю, рекомендация равна `0`.

Формула MVP не включает lead time, товары в пути, резерв, сезонность или
настраиваемый горизонт. Текст рекомендации отдельно напоминает учитывать время
приёмки; он не должен создавать впечатление, что это время уже включено в
число.

### 7.4 Оценка упущенных продаж

```text
EstimatedMissedSales(product)
    = AverageDailySales(product, P) × OutOfStockDays(product)
```

Результат — оценка недополученных единиц, а не рублей и не гарантированная
продажа. `OutOfStockDays` считается по сохранённой SellerScope ежедневной
истории остатков, а не восстанавливается из текущего WB stocks-report.

## 8. Главный сигнал

Для товара показывается максимум один `PrimarySignalData`. Положительная
динамика не перекрывает операционный риск.

Строгий порядок категорий:

1. текущий остаток равен нулю;
2. `0 < StockCoverage ≤ 3` дня;
3. `3 < StockCoverage ≤ 7` дней;
4. критичный рост Returns Rate или падение Buyout;
5. существенное падение Sales;
6. нет значимого отклонения.

Сигнал содержит:

- `type` и числовой `priority`;
- факт;
- риск;
- рекомендацию;
- evidence с исходными рассчитанными значениями;
- `calculated_at` и data revision.

Пример для канонического товара:

```text
Факт: 28 шт. в наличии
Риск: хватит примерно на 4 дня
Рекомендация: запланируйте поставку с учётом времени приёмки
```

### 8.1 Требующее согласования

Утверждённые материалы пока не задают:

- численный threshold критичного роста Returns Rate;
- численный threshold падения Buyout;
- численный threshold существенного падения Sales;
- tie-breaker между двумя фактами внутри одинакового priority;
- длительность периода без продаж для view «Без движения».

Эти значения должны стать явными именованными configuration/domain constants и
получить тестовые примеры до реализации соответствующих сигналов. До
согласования нельзя подставлять случайные проценты или скрытые magic numbers.
Stock priorities 1–3 уже определены и от этих thresholds не зависят.

## 9. Что считается заранее и по запросу

Заранее после импорта:

- `AccountDailyMetric`;
- `ProductDailyMetric`;
- актуальные `ProductSignal`;
- counters продуктовых и stock views;
- последний stock snapshot;
- ежедневное значение запасов SellerScope.

По запросу:

- сумма KPI за диапазон;
- comparison с предыдущим периодом;
- day/week grouping готовых daily metrics;
- backend filtering, sorting и pagination;
- вклад товара в изменение;
- актуальный stock forecast и RecommendedSupply.

Queue выполняет rebuild затронутых daily aggregates и signals, ночной
safety-rebuild последних изменённых дней и backfill после изменения normalizer
или формулы.

## 10. Cache и data revision

Redis хранит только короткий cache готового query result. Источником истины
остаются PostgreSQL facts и aggregates.

Cache key включает как минимум:

```text
seller_account_id
current period
comparison period
timezone
granularity
filters / sorting / page
data revision
```

Успешная синхронизация увеличивает data revision. Результаты предыдущей revision
не используются, даже если их TTL ещё не истёк.

## 11. Канонический Demo-MVP fixture

Текущий период: `1–31 июля 2026`.  
Comparison: `1–30 июня 2026`.

### 11.1 Кабинет

| Метрика |   Июль 2026 |   Июнь 2026 | Отображаемое изменение |
| ------- | ----------: | ----------: | ---------------------: |
| Revenue | 1 284 600 ₽ | 1 142 883 ₽ |                 +12,4% |
| Orders  |       1 842 |       1 695 |                  +8,7% |
| Sales   |       1 471 |       1 335 |                 +10,2% |
| Buyout  |       79,9% |       78,8% |              +1,1 п.п. |

Точные проверки до UI-округления:

```text
Revenue change = (1 284 600 - 1 142 883) / 1 142 883 × 100
               ≈ 12.39995695%

Orders change  = (1 842 - 1 695) / 1 695 × 100
               ≈ 8.67256637%

Sales change   = (1 471 - 1 335) / 1 335 × 100
               ≈ 10.18726592%

July Buyout    = 1 471 / 1 842 × 100 ≈ 79.85884908%
June Buyout    = 1 335 / 1 695 × 100 ≈ 78.76106195%
Delta          ≈ 1.09778713 percentage points
```

Июньские целые baseline values выбраны как детерминированные значения,
воспроизводящие утверждённые округлённые изменения. Seeder, backend tests и UI
не должны использовать разные baseline.

Для июля:

```text
NotBought = max(1 842 - 1 471, 0) = 371
```

### 11.2 Проблемный товар

Канонический товар: «Подушка Memory 50×70».

```text
CurrentStock = 28 units
AverageDailySales = 7 units/day
StockCoverage = 28 / 7 = 4 days
RecommendedSupply = max(0, 7 × 30 - 28) = 182 units
```

Главный сигнал относится к priority 3: «Закончится примерно через 4 дня».
Положительная sales dynamics остаётся видимой отдельно, но не заменяет риск
дефицита.

## 12. Представление и округление

- деньги форматируются из копеек и не теряют внутреннюю точность;
- KPI mockups показывают целые рубли с неразрывными разделителями;
- quantities отображаются целыми единицами;
- percentage и percentage-point changes по умолчанию показываются с одним
  десятичным знаком;
- знак `+` используется только для положительного изменения;
- изменение доли всегда подписывается `п.п.`, а не `%`;
- сложная метрика получает tooltip с формулой, периодом и источником;
- в ViewModel передаются raw calculated value и готовое безопасное display
  value, чтобы React не дублировал правила округления.

## 13. Data-quality states

Любая метрика, зависящая от отсутствующего или неполного resource, должна
различать:

- настоящее нулевое значение;
- `null` из-за нулевого denominator;
- ресурс ещё синхронизируется;
- ресурс недоступен из-за WB permissions;
- последний успешный факт устарел;
- отдельный resource завершился ошибкой.

Нельзя заменять неизвестное значение нулём. ViewModel передаёт значение вместе
с availability/status и timestamp последнего успешного обновления.

## 14. Минимальные unit tests

До использования метрик в UI обязательны тесты:

1. canonical July/June KPI и округлённые изменения;
2. Buyout и Returns Rate с обычным и нулевым denominator;
3. NotBought с обычной и отрицательной разницей;
4. AverageDailySales с днями без продаж;
5. StockCoverage для `0`, положительного stock и отсутствия продаж;
6. RecommendedSupply с положительным результатом и нижней границей `0`;
7. EstimatedMissedSales по сохранённым out-of-stock days;
8. signal priority, где stock risk перекрывает положительную динамику;
9. calendar-month и arbitrary-range comparison;
10. timezone boundary около полуночи UTC.
